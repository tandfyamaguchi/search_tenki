# 「天気」記事検索 — 管理・日常運用

本番環境でDjango adminを使って記事データを管理したり、定期更新を行ったりする方法を記述しています。新規導入、PHP版からの切替、Webサーバー設定は [README_ini.md](README_ini.md)、実装の説明は [README_prog.md](README_prog.md) を参照してください。

以下の `python manage.py` コマンドは、対象のPython環境を有効化してから実行します。例）`conda activate search-tenki-dj52`

## 1. 運用上の禁止事項

次の操作は通常運用で行いません。

- `etenki.db` への書込み、`migrate --database=etenki` の実行。
- 初回同期後の `python manage.py initialize_search_db --apply` の再実行。
- `static/` 内の配信用ファイルを直接編集すること。
- `DJANGO_DEBUG=1` を公開状態で有効にすること。

## 2. 管理画面の基本

管理画面の入口は `/admin/` です。初回導入時に `createsuperuser` で作成した利用者は全権限を持ちます。

記事の日常操作は、ホームにある案内どおり「発行管理」→「巻」→対象の「号」から始めます。号の行で「この号に記事を追加」または「この号の記事を編集」を選びます。

パスワードを忘れた場合
```sh
cd ./search_tenki
conda activate search-tenki-dj52
python manage.py changepassword '<管理者ID>'
```

## 3. adminで操作できる範囲

現在の実装でadminに登録されているデータは次のとおりです。

|admin上の対象|主な内容|公開画面への影響|運用上の注意|
|---|---|---|---|
|`記事`|題名、巻、号、開始頁、PDF、カテゴリ、内容分類、著者、キーワード|検索結果と記事表示|通常は「発行管理」→「巻」→「号」から追加・編集する。|
|`カテゴリ`|カテゴリ名、原稿種別、使用中の記事数|詳細検索のカテゴリ表示、記事のカテゴリ|原稿種別を必ず指定する。使用中のカテゴリは削除できない。|
|`内容分類`|内容分類名、使用中の記事数|詳細検索、記事の内容分類|追加・変更できる。使用中の内容分類は削除できない。|
|`キーワード`|キーワード名、使用中の記事数|検索結果、記事のキーワード|追加・変更できる。使用中のキーワードは削除できない。|
|`原稿種別`|原稿種別名、表示順、カテゴリ数|詳細検索のカテゴリの並び|カテゴリを含む原稿種別は削除できない。|
|`著者`|著者名、使用中の記事数|記事の著者表示|既存の表記はadminから変更できない。未使用の著者名だけを削除できる。|
|`Year`（巻）|発行年、巻番号、所属する号|巻の選択画面|「発行管理」内の「巻」から追加する。|
|`Month`（号）|号番号、開始頁|号の選択画面、巻号検索|単独メニューには表示されない。対象の巻を開いて管理する。|
|標準の「ユーザー」「グループ」|管理者アカウントと権限|adminの利用可否|個別アカウントと最小権限を守る。|

カテゴリ、内容分類、キーワード、原稿種別は「記事管理」に表示されます。カテゴリ・内容分類・キーワード・原稿種別の名称や表示順を変更すると、既存記事と公開検索にも反映されます。

## 4. 巻・号（Year / Month）の管理

adminの「発行管理」内にある「巻」で管理します。巻一覧には巻番号、発行年、登録号数、登録済みの号が表示されます。対象の巻を開くと、その巻の号だけを表形式で表示します。表には号番号、号の開始頁、記事数、操作が並びます。`Month`（号）は単独メニューに表示されません。

### 巻と号を追加・編集する場合

1. 新しい巻が必要な場合だけ「巻を追加」から巻番号と発行年を入力して保存する。
2. 対象の巻を開き、「号を追加」から号番号と開始頁を入力する。保存後は発行管理の表へ戻る。
3. 通常号・特別号を問わず、必要な号は「号を追加」から1件ずつ登録する。開始頁は自動推測しない。
4. 表の登録号・開始頁・記事数を確認する。「この号に記事を追加」は掲載先を指定済みの記事追加画面を開く。
5. 既存記事を扱う場合は「この号の記事を編集」を選ぶ。対象の巻・号で絞り込まれた記事一覧が開くので、記事の題名を選んで編集する。
6. 公開画面で対象巻を開き、号が番号順に表示されることを確認する。

既存記事がある巻番号・号番号は変更・削除できません。

## 5. 記事（Kijis）の管理

記事の追加・変更・削除は、通常は「発行管理」→「巻」→「号」から行います。「記事管理」→「記事」から直接操作することもできますが、巻・号を誤らないため前者を優先します。

### 記事を追加する場合

1. カテゴリ、内容分類、キーワードは、先に「記事管理」の各マスタで管理してから選択する。
2. まず「発行管理」の「巻」で、掲載先の巻と号を登録する。対象号の「この号に記事を追加」から開くと、巻・号が最初から選択されている。
3. 題名、巻、号、記事の開始頁を入力する。巻を選ぶと、その巻に登録済みの号だけが候補に表示される。
4. 「著者（公開表示順）」の表で、公開する順に著者と表示順を入力する。筆頭著者を1、次を2とする。同じ著者または同じ表示順は登録できない。
5. PDFの相対パスを入力する。この画面はPDFのアップロード機能ではない。
6. 保存後に公開画面で検索し、巻・号、開始頁、著者順、PDFリンクを確認する。

追加・変更画面で「入力を破棄して元の画面に戻る」を選んだ場合、記事の作成・変更は行われません。ただし、記事追加前に別画面で作成したマスタや著者名は残ります。不要なら使用中の記事数が0であることを確認してから削除してください。

## 6. カテゴリと原稿種別の管理

詳細検索画面のカテゴリ表示は、運用DBに保存した次の情報で決まります。

- `CategoryGroup`: 原稿種別の名称と表示順。
- `Category.group`: 各カテゴリが所属する原稿種別。
- `Category.name`: カテゴリの正式名称。

カテゴリを追加・変更したときは、次の順で操作します。
1. 「記事管理」→「原稿種別」で名称と表示順を登録・確認する。
2. 「記事管理」→「カテゴリ」で所属する原稿種別を指定する。
3. 詳細検索画面で表示順、名称、選択状態を確認する。

新規導入時の原稿種別25件とカテゴリID 1〜206の対応は、`basemodel/initial_data/` のCSVを正本として管理します。初期同期後の通常管理では、CSVを再投入せずDjango adminを使います。

## 7. 定期確認と障害時の切り分け

リリース前、カテゴリ・原稿種別の変更後、または障害調査時には、次を確認します。

```sh
python manage.py check
python manage.py test
python manage.py makemigrations --check --dry-run
python manage.py migrate --plan
```

本番の環境変数を読み込める管理環境では、`python manage.py check --deploy` も実行し、HTTPS関連の警告を記録・解消します。詳細は [README_ini.md](README_ini.md) を参照してください。

|症状|最初に確認すること|避けること|
|---|---|---|
|400エラーやHost拒否|`DJANGO_ALLOWED_HOSTS` とプロキシが渡すHost名|公開中に`DEBUG=1`へ変更すること|
|CSS・画像・admin装飾が404|`collectstatic` の結果、`/static/` のWebサーバー設定、読み取り権限|`static/` を直接編集すること|
|DBが書込み不可・ロックされた|`db.sqlite3` と親ディレクトリの権限、バックアップや同時処理、SQLite配置|`etenki.db` へ書き込むこと|
|初期同期コマンドが停止|空DBであること、CSVと読取り専用旧DBの整合|運用DBで再実行すること|
|更新後に画面が壊れた|適用したコード版、migration計画、静的ファイル、サービスログ|DBを無断で戻す・migrationを無計画に逆適用すること|

## 9. 既存Django環境の定期更新

通常の更新手順は次のとおりです。
1. 配布するGitコミット、変更内容、対象migrationをレビューする。
2. 本番DBの一貫性を確認したバックアップを取得し、復元手順を確認する。
3. ステージングで `check`、テスト、`migrate --plan`、公開画面、admin操作を確認する。
4. 本番で `migrate --database=default --plan` を再確認し、承認済みの場合だけ `migrate --database=default` を実行する。
5. `python manage.py collectstatic --noinput` を実行し、WSGIサービスを再起動する。
6. 検索、静的ファイル、adminログイン、ログ、DB書込みを確認し、実施結果を記録する。

既存運用DBの更新では、`initialize_search_db` を使いません。ロールバックはコード、静的ファイル、DB migration、データの関係を確認してから行い、必要なら検証済みバックアップから復元します。
