# 「天気」記事検索 — 管理・日常運用

この文書は、本番環境でDjango adminを使う運用担当者向けです。環境構築、デプロイ、初期管理者の作成は [README_ini.md](README_ini.md) を参照してください。

以下の `python manage.py` コマンドは、Minicondaの `search-tenki-dj52` 環境を `conda activate search-tenki-dj52` で有効化してから実行します。

## 1. 管理画面の基本

管理画面の入口は `/admin/` です。個別の管理者アカウントでログインし、操作履歴を追跡できるようにしてください。初回導入時に `createsuperuser` で作成した利用者は全権限を持ちます。



パスワードを忘れた場合は、サーバーの管理者が対象アカウントを指定して次を実行します。新しいパスワードは対話入力します。

```sh
cd ./search_tenki
conda activate search-tenki-dj52
python manage.py changepassword '<運用担当者の個別ID>'
```

## 2. 現在adminで操作できる範囲

現在の実装でadminに登録されているデータは次のとおりです。

|admin上の対象|主な内容|公開画面への影響|運用上の注意|
|---|---|---|
|`Kijis`（記事）|題名、巻、号、開始頁、PDF、カテゴリ、内容分類、著者、キーワード|検索結果と記事表示|初回同期後はadminを正本として追加・変更する。`makemodel`は再実行しない|
|`Year`（巻）|発行年、巻番号、所属する号|巻の選択画面|「発行管理」内の「巻」から追加・変更する|
|`Month`（号）|号番号、開始頁|号の選択画面、巻号検索|単独メニューには表示されない。対象の巻を開いて追加・変更する|
|標準の「ユーザー」「グループ」|管理者のアカウントと権限|adminの利用可否|最小権限と個別アカウントを守る|

`Category`、`Bunrui`、`Author`、`Keyword`、旧DBのモデルは、現在adminに単独の管理画面がありません。記事の編集フォームで既存の関連データを選ぶことはできますが、カテゴリ・著者・キーワード・内容分類を単独で新規追加、修正、削除する画面はありません。

そのため、これらのマスターデータをadminから直接管理したい場合は、別途機能追加が必要です。運用担当者が本番サーバー上のPythonファイルやSQLiteファイルを直接編集して代替してはいけません。

## 3. 操作前・操作後の共通手順

本番データを変更する前に、必ず次を実施します。

1. 変更目的、対象レコード、予定日時、作業者、承認者を記録する。
2. `db.sqlite3` のバックアップが成功しており、復元先と復元担当者が明確であることを確認する。SQLiteのバックアップは、アプリケーションと同じディレクトリに置かない。
3. adminへの同時ログイン、バックアップ、リリース作業が重なっていないことを確認する。
4. 対象レコードを検索し、IDと現在値を二者で確認する。

変更後は、次を実施します。

1. adminの変更履歴で、作業者、時刻、変更内容を確認する。
2. 公開画面の巻・号検索または詳細検索で、意図した結果になることを確認する。
3. 変更記録に結果と確認者を残す。
4. 異常時は追加の修正を重ねず、公開を止める必要性とバックアップからの復元を責任者へ連絡する。復元は、あらかじめ検証済みの組織手順だけで実施する。

SQLiteは同時書き込みに弱いため、管理操作は原則として一人ずつ行います。

## 4. 巻・号（Year / Month）の管理

通常の入口はadminの「発行管理」内にある「巻」です。巻一覧には巻番号、発行年、登録号数、登録済みの号が表示されます。対象の巻を開くと、その巻に属する号だけを表形式で追加・変更できます。`Month`（号）は単独メニューに表示されません。

### 巻と号を追加する場合

1. 「巻を追加」から巻番号と発行年を入力する。
2. 同じ画面下部の「この巻の号」で、号番号と開始頁を入力する。複数の号は「もう1つの号を追加」で続けて入力できる。
3. 保存後、巻一覧の登録号数と登録済みの号を確認する。
4. 公開画面で対象巻を開き、号が番号順に表示されることを確認する。

通常号を1〜12号まで事前に一括登録しません。巻によって号数が異なり、特別号もあり得ます。公開画面には登録済みの号が表示されるため、記事が未登録の号を追加すると空の一覧へ遷移します。発行済みで必要な号だけを登録し、記事も続けてadminから追加してください。

巻番号と、同じ巻内の号番号は重複登録できません。新しい制約を適用するため、リリース時には `python manage.py migrate --database=default` を実行します。既存の巻番号や号番号を変更すると記事の巻・号との対応が崩れるため、通常運用では変更せず、追加で扱ってください。

巻の変更画面で号を操作するには、担当者に `Year` の閲覧・追加・変更権限と、`Month` の閲覧・追加・変更権限を付与します。`Year` を削除しようとすると、紐付く `Month` が存在する間は保護され、削除できません。巻・号の削除は公開画面から該当導線を失わせるため、通常運用では削除せず、責任者の承認とバックアップ、二者確認がそろった場合だけ実施してください。

## 5. 記事（Kijis）の管理

初回同期が完了した後の `Kijis` は、検索用DB（`db.sqlite3`）とDjango adminを正本として管理します。記事の追加・変更・削除は、承認、バックアップ、変更記録、公開画面での確認を行ったうえでadminから実施します。旧DB（`etenki.db`）は初回データ投入の参照元であり、日常運用で変更したり、記事更新のために再同期したりしません。

記事の巻・号は公開画面の検索条件に使われます。記事を追加する際は、先に対応する巻と号を登録し、入力値が一致していることを確認してください。記事入力画面の巻・号選択と関連データの入力補助は、別途のadmin改修で追加します。

## 6. 初回導入時だけの旧DB同期

`etenki.db` は初回投入専用の参照元で、`db.sqlite3` は運用DBです。初回導入時だけ、admin運用を開始する前に次の順番で同期します。

1. データ責任者の承認と、`db.sqlite3`・`etenki.db` の整合したバックアップを確認する。
2. adminの書き込みとリリース作業を止める。
3. 検証モードを実行し、エラーと更新予定を確認する。

```sh
cd /path/to/python_GPT2
conda activate search-tenki-dj52
python manage.py makemodel --dry-run
```

4. 検証結果を承認した場合だけ通常同期を実行する。

```sh
python manage.py makemodel
python manage.py validate_category_groups
```

初回同期の完了後は、`makemodel` を検証モードを含めて再実行してはいけません。以後の記事、巻、号の変更はadminで行います。同期でエラーが出た場合も、回避のために本番DBや旧DBを直接変更してはいけません。

## 7. カテゴリ分類設定の確認

詳細検索画面のカテゴリ表示は、次の2つで決まります。

- DBの `Category`: カテゴリIDと画面に表示する正式名称
- `search/category_groups.py`: 各カテゴリIDを25種類の原稿種別へ分類する設定

`validate_category_groups` は、DBと設定にあるカテゴリIDの集合が一致するかだけを検査する読み取り専用コマンドです。

```sh
python manage.py validate_category_groups
```

正常な場合は、次のように表示されます。

```text
カテゴリ分類IDはDBと一致しています（206件）。
```

カテゴリIDがDBにだけある場合は、公開画面の詳細検索で設定エラーになります。設定にだけ存在するIDがある場合も同様です。カテゴリを追加・削除・分類変更する場合は、データ責任者と開発担当者が次を一つの変更として扱います。

1. データ更新の承認とバックアップを確認する。
2. DBのカテゴリIDと名称を確認する。
3. 開発担当者が `search/category_groups.py` の適切なグループを変更し、IDを重複登録しないことを確認する。
4. ステージングで `python manage.py validate_category_groups` を実行する。
5. コードとデータを同じリリースとして反映し、詳細検索画面で表示位置と名称を確認する。

カテゴリ名はDBの `Category.name` を表示します。`category_groups.py` 内のID横の名称コメントは管理上の参考情報であり、画面表示には使われません。設定ファイルを本番サーバー上で直接編集するのではなく、通常のコードレビューとリリース手順を使ってください。

## 8. バックアップ、障害、セキュリティ

- `db.sqlite3` は検索データだけでなく、管理者、権限、セッション、adminの操作履歴も保持します。バックアップ対象から除外しません。
- `etenki.db` は変更禁止の参照元です。ファイルの書き込み権限を外し、運用DBとは別にバックアップします。
- SQLiteの復元は、アプリケーション停止、対象ファイルの特定、整合したバックアップ、ステージングでの復元確認を要します。緊急時に推測でファイルを上書きしないでください。
- 管理画面はHTTPSで提供し、VPNまたはIP制限などでアクセス元を制限します。`DJANGO_DEBUG=0`、シークレットの安全な保管、個別アカウントを必須とします。
- 本番URL、初期パスワード、`DJANGO_SECRET_KEY`、バックアップの保存先などの機密情報を、この文書やソースコードに書かないでください。

## 9. 定期確認

少なくともリリース前、初回同期後、カテゴリ変更後には、次を確認します。

```sh
python manage.py check
python manage.py check --deploy
python manage.py validate_category_groups
```

```sh
python manage.py test
```
